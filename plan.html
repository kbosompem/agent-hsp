Agent HSP

A local-first worship presentation app. It combines PewBeam's real-time AI scripture agent, VideoPsalm's complete manual presentation toolkit, and a new cue-driven automation engine that can run parts of a service on its own. Two modes: Manual and AI. Every model runs on the machine. No cloud, no subscription, no transcription metering.

01 · Overview

What we are building, and why

PewBeam is a desktop app (launched Feb 2026) that listens to a live sermon, transcribes it, and puts the referenced Bible verse on screen within about two seconds, including paraphrased references. It is AI-only: it does scripture, not songs, and it is a subscription ($14 to $30 per month) with metered transcription on the free tier.

VideoPsalm is a free, full worship presentation suite: songbooks with instant search, thousands of Bible translations, bilingual display, chords with transposition, video loops under lyrics, alerts, countdowns, auto-played music, PowerPoint import, CCLI support. It is manual-only, Windows-only, and aging.

Agent HSP is the union of the two, plus one thing neither has: a cue engine that listens for spoken cues like "it's time for praise and worship" and runs scripted sequences (splash screen, then the soundtrack with synced lyrics). And it works with zero internet, because every AI model runs locally.

Non-goals for v1

  • No mobile or web companion app.
  • No cloud sync, accounts, or telemetry.
  • No livestream production tools. We complement OBS by sending clean output over NDI.
  • No AI voice or sermon generation. The AI listens and displays. It never speaks or edits the sermon.
02 · Product definition

Two modes, three autonomy levels

The core ask is "manual or AI." Manual mode is a complete VideoPsalm-class operator console with the AI completely off. AI mode turns on the listening pipeline, and inside it the operator picks how much authority the AI gets.

Manual

Operator drives everything: agenda, slides, verses, songs, videos, alerts. Zero AI code runs. This is Sunday-safe from day one and is the fallback if the machine or microphone misbehaves.

AI Copilot default

The AI listens and suggests. Every detected verse or cue appears as a card with a countdown. One key approves, one key skips. If the countdown expires, low-risk actions (verse display) auto-fire; risky ones just expire.

AI Autopilot

The AI acts on whitelisted action types automatically, with a visible grace window to cancel. The operator can demote to Copilot or hold everything with one key at any moment.

Two ways the AI knows what to do

SourceHow it worksExample
Listen mode (free-run)No plan is loaded. The AI reacts to whatever it hears: spoken verse references, quoted passages, and any cue phrases you have defined globally."As Paul says in Romans five eight..." shows Romans 5:8.
Script mode (given a list)An order of service is loaded. Each item carries cue phrases and actions. The AI aligns the live transcript to the script, auto-advances, and still handles off-script verses and cues."Let's enter into praise and worship" fires the Praise item: 12-second splash, then the soundtrack with synced lyrics.

Safety rules (non-negotiable)

  • Hold key: one key (H) freezes every queued AI action. No action fires while held.
  • Panic: Shift+Esc blacks out all outputs and cancels the queue, in any mode.
  • Confidence floors: below-threshold detections never auto-fire; they only log.
  • Cooldowns: the same verse or cue cannot refire within a configurable window (default 3 minutes).
  • Everything is logged: transcript plus every AI decision is saved per session for review after the service.
Hat 1 · UI / UX

Every screen, mocked up

Wireframes below are structural mockups, not final art. Operator screens are dark for a dark room; congregation output uses themes designed separately. Gold numbered markers call out the decisions that matter.

Design principles

  • Keyboard first. A service can be run without touching the mouse. Every AI suggestion is one keystroke to accept or reject.
  • Glanceable trust. The operator always knows what the AI heard, what it decided, and what happens next, without reading paragraphs.

  • Dark room operator UI, bright congregation output. The app never blinds the operator; the projector output never looks like the app.
  • Manual is always one click away. Mode switching is instant and mid-service safe.
  • Zero setup Sundays. Open the app, pick the schedule, press Go.

Data model (SQLite)

  • songs, songbooks, song_slides (ordered lyric slides), chord_pro, attached audio and LRC timing per song.
  • bibles (one table set per translation, FTS5 indexed), verse text + canonical reference IDs.
  • verse_vectors (precomputed embeddings for semantic search, built once per translation).
  • schedules, schedule_items (type, payload, cue phrases, action stacks, per-item autonomy).
  • cue_rules (global cues that work in listen mode without a schedule).
  • sessions, transcript_events, action_log (what fired, what was canceled, what was overridden).
  • themes, media_assets, settings.
  • Schedules also export as a portable .preso JSON file (VideoPsalm's "portable agenda" idea): copy it between home and church machines.

Content strategy

  • Bundled Bibles: KJV and WEB (public domain). Other translations arrive via importers (OpenLP, Zefania, OSIS) so the church brings its own licensed files. No NIV/ESV redistribution.
  • Songs: manual entry plus importers: CCLI SongSelect (.usr), OpenLP, plain text, and plain CSV. CCLI number field on every song for reporting.
  • Media: any MP4/WebM video, MP3/WAV audio, images. Themes bundle backgrounds.
  • Fonts: bundle one OFL serif and one OFL sans so output looks identical on Windows and macOS.

Cross-platform gotchas we plan for now

  • Webview differences: standardize output video on H.264 MP4 (+ WebM); test both webviews. CSS animation performance is fine on both.
  • Integrated GPUs: the first-run wizard benchmarks CPU against Vulkan on the iGPU and keeps the faster path; machines with weak iGPU drivers quietly stay on CPU.
  • macOS: microphone permission prompt (info.plist usage string), hardened runtime, notarization. Desk feed over USB is a plain input device, so no virtual-audio dependency for the core flow.
  • Windows: WASAPI loopback is native (nice for capturing tracks played from the same machine); code-signing cert for SmartScreen reputation.
  • Lyric sync: the audio sample clock lives in Rust, not the webview, so lyrics never drift from the soundtrack.

Audio wiring: XR16 to the laptop

  1. Connect the XR16's USB-B port (the square connector on the back) to the laptop. The built-in X-USB card shows up in Windows as a 16-in / 4-out audio device, no driver needed.
  2. In X-Edit or the console app: Routing → Card. Assign Card Out 1 to a spare Mixbus (say Mixbus 6, named "Transcript").
  3. Send the pulpit mic post-fader at unity, plus a little of the worship leader, to that bus. Keep the bus out of the main mix path so the feed stays steady no matter what the sound desk does mid-service.
  4. Set the bus so speech peaks around -18 to -12 dBFS. Too hot clips; too low starves the transcriber.
  5. In the app: input device "X-USB" (or "Behringer XR16"), channel 1, mono. The browser alpha reads it as a normal microphone.
  6. No X-USB handy? Any USB interface (Scarlett 2i2) fed from an aux send works identically.

Testing

  • Fixture sermons: ten recorded services with labeled verse references and cue timestamps, replayed through the whole pipeline in CI. We assert detection rate, false positives, and latency on every commit.
  • Reference parser corpus: hundreds of spoken reference forms ("third chapter of John", "rom five eight", "jn three sixteen") as unit tests.
  • Visual regression: golden screenshots of output slides on both platforms.
  • E2E: tauri-driver (WebDriver) for operator flows.

Hat 3 · AI engineering

Local models for listening, verses, and cues

Everything below runs on the church machine. No API keys, no internet requirement, no per-minute billing. The stack is deliberately boring: Whisper for ears, a small LLM for judgment, embeddings for meaning, and plain code for everything that does not need a model at all.

Principles

  • Deterministic first. "John 3:16" is a regex problem, not an LLM problem. Models handle only what code cannot: paraphrase, ambiguity, intent.
  • Smallest model that passes the tests. A 3B model beats 70B on this task if it fits the budget and answers in 300 ms.
  • Graceful degradation. No GPU: drop the LLM, keep regex + embeddings. Low RAM: embeddings only. No models at all: manual mode with a warning. The app never bricks a Sunday.
  • Every decision is overridable, logged, and reviewable.

The pipeline, end to end

  1. Capture: 48 kHz mono from the desk feed, resampled to 16 kHz.
  2. VAD: Silero slices speech segments; a segment closes after ~0.6 s of silence.
  3. Streaming STT: Whisper runs on a rolling window and emits partial text ~2 times per second, so refs are detected mid-sentence, not after a pause.
  4. Transcript bus: every partial and final is timestamped and broadcast to three listeners: verse detector, cue matcher, script aligner.
  5. Verse detection (two paths): exact reference parsing (regex + fuzzy book-name table), and paraphrase matching (embed the last ~15 s of transcript, cosine search the verse index, top-k candidates).
  6. LLM verify: for candidates above threshold, a 3B model answers a strict yes/no ("is the speaker quoting or referencing Romans 5:8?"). This is what kills false positives from generic God-talk.
  7. Cue matching: schedule cues were embedded at load time; the rolling transcript window is compared to each. Gray-zone scores get an LLM confirm; clear scores fire.
  8. Action engine: fires or proposes according to autonomy settings, honoring holds, cancel windows, cooldowns, and priorities.

Verse detection detail

  • Path A, exact references: a parser built for spoken forms: "rom 5 8", "Romans chapter five verse eight", "third chapter of John, verse sixteen". This path alone catches most sermon references, in milliseconds.
  • Path B, quotes and paraphrases: the pastor says "while we were still sinners Christ died for us" without naming the verse. The transcript window embedding is matched against 31k verse embeddings; a strong match plus LLM confirmation displays Romans 5:8. This is PewBeam's headline feature, done locally.
  • Dedup: same verse within 3 minutes is ignored (configurable). Adjacent verses roll up into ranges (Romans 5:8-9) instead of flashing card by card.
  • Long passages: a detected reference to Romans 5 preloads verses 1-5 as next slides, so the operator just presses Space.

Cue engine detail

A cue is data, not code. From the schedule builder, one item looks like this internally:

{
  "item": "Praise & Worship",
  "cues": [
    { "phrase": "it's time for praise and worship" },
    { "phrase": "let's enter into praise" },
    { "phrase": "worship team, come up" }
  ],
  "match": { "type": "semantic", "threshold": 0.72 },
  "actions": [
    { "type": "splash", "template": "praise", "duration_s": 12 },
    { "type": "play_track", "track": "total-praise.mp3",
      "lyrics": "total-praise.lrc", "fade_in_s": 1.5 }
  ],
  "autonomy": "auto", "cancel_window_s": 6, "cooldown_s": 600
}
  • Matching is semantic, not keyword: "let us lift our hands in worship" should hit the praise cue even though no phrase matches word for word. Embeddings handle this; exact-phrase hits get a score boost.
  • Debounce: a cue only fires on a completed phrase (VAD boundary or sentence end), never mid-sentence.
  • Global cues (no schedule needed) work in listen mode: define "nursery call" style cues that highlight the alert composer pre-filled, never auto-send.
  • Test bench: the "test cue" button in the schedule builder types or speaks a phrase and shows the match score against every cue in the schedule.

Script alignment detail

  • Each schedule item gets an expected-content embedding (title, songs, themes, preacher notes if pasted in).
  • The aligner scores the recent transcript against upcoming items, with hysteresis: item N must beat item N+1 by a margin for 2 consecutive windows before the pointer moves.
  • The pointer can also be moved manually at any time; the aligner treats operator jumps as ground truth and re-anchors.
  • This is what lets the app "follow a script" without the operator touching anything, while still catching off-script verses and cues.

RAM budget on the launch laptop

  • Windows 11 idle: ~4.5 GB
  • Preso app + webview windows: ~1.5 GB
  • Whisper small.en (loaded while listening): ~0.8 GB
  • Embeddings + verse index: ~0.5 GB
  • Llama 3B (on demand, unloaded after 5 min idle): ~2.3 GB
  • Headroom remaining: ~6 GB

Honest accuracy expectations

  • Whisper small.en on a clean desk feed: roughly 5-8% word error rate. A noisy room mic degrades that; the fix is a better feed, not a bigger model.
  • Targets we will hold ourselves to on the fixture corpus: over 90% of spoken references detected, under 1 false verse per 10 minutes in Copilot, median latency under 1.5 s on the recommended tier.
  • A custom vocabulary boost (book names, preacher's favorite phrases, church member names for alerts) is loaded as Whisper's initial prompt. Cheap and effective.

Privacy

  • Audio never leaves the machine. Transcripts and decision logs are stored locally, optionally auto-deleted after N days.
  • No account, no telemetry, no phone-home checks. The app is fully functional offline forever.

08 · Risks

What could go wrong, and the plan for each

RiskSeverityMitigation
Accents, room noise, or a bad mic degrade transcriptionHighInsist on a desk feed (USB interface), not a room mic. Custom vocabulary boost. Fallback model tiers. Manual mode always works.
False-positive verses distract the congregationHighCopilot is the default; LLM verification; confidence floors; dedup and cooldowns; one-key skip. Autopilot is opt-in per item.
The church PC is too weak for the recommended tierMediumFirst-run hardware check picks the tier; CPU-only path with tiny/base models is first-class, not an afterthought.
Webview video codec differences between Windows and macOSMediumStandardize on H.264 MP4 + WebM; visual regression tests on both platforms; reject unsupported files at import with a clear message.
Bible translation licensingMediumBundle only KJV/WEB; importers let the church load translations it already licenses. Never redistribute copyrighted text.
NDI SDK is closed-sourceLowOptional module, off by default; the core projector output never depends on it.
Scope creep from VideoPsalm parityHighPhase gates above; parity features marked must/should/later; every phase ships something usable on Sunday.
Solo-developer bandwidthMediumThe roadmap assumes one dev; P1 alone is already a deployable product if everything else slips.
